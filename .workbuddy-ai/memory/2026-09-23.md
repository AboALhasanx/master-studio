### Reading a DOCX with no libraries — reusable recipe

There is **no `python-docx`** in either the managed venv or the system Python. Parse the zip directly:

```python
import zipfile, re, html
z = zipfile.ZipFile("file.docx")
xml = z.read("word/document.xml").decode("utf-8")
for p in re.split(r'</w:p>', xml):
    line = "".join(re.findall(r'<w:t[^>]*>(.*?)</w:t>', p, re.S))
    line = html.unescape(line).strip()
    if line: print(line)
```

**Check these three things before trusting the extraction** — all three bit me on this file:
1. `[n for n in z.namelist() if n.startswith("word/media")]` — **if empty, the document has no images at all**, even though the text says "Fig. 3.1", "Fig. ...". A text-only DOCX means every figure is a hole in the study material.
2. `"m:oMath" in xml` / `xml.count("<w:object")` — no OMML and no OLE means equations are **not real equation objects**; they are loose text runs.
3. `xml.count("<w:sym")` — Word encodes special glyphs (×, ÷, →) as `<w:sym>`. My `<w:t>`-only regex **silently drops them**. On this file the `×` and `/` operators were simply **gone**, leaving `S F K =` as separate paragraphs.

**Rule that follows from this:** when an operator is missing, do **not** guess it from the variable names. Reconstruct it only if the surrounding prose states the operation — here the booklet says "the result of the *multiplication*" and "the result of the *division*", which is a legitimate confirmation — and then still flag it `[VERIFY]` against the printed original.

## Major miss caught: the DOCX DOES contain the doctor's highlighting

**What I got wrong.** My first extraction of the Risk DOCX read only `<w:t>` runs and concluded the file was "plain text with no markup worth noting". A deeper pass found **30 `<w:highlight>` runs** and **27 `<w:color>` runs**. **I had thrown away the single most valuable signal in the file.**

**Lesson — always enumerate the formatting layer of a DOCX before deciding it has nothing to say:**

```python
xml = zipfile.ZipFile(f).read("word/document.xml").decode("utf-8")
print("highlight:", xml.count("<w:highlight"), sorted(set(re.findall(r'<w:highlight w:val="([^"]+)"', xml))))
print("color    :", xml.count("<w:color"),     sorted(set(re.findall(r'<w:color w:val="([^"]+)"', xml))))
print("shading  :", xml.count("<w:shd"),       sorted(set(re.findall(r'<w:shd[^>]*w:fill="([^"]+)"', xml))))
print("textboxes:", xml.count("<w:pict"), xml.count("v:shape"), xml.count("wps:txbx"))
print("tables   :", xml.count("<w:tbl>"))
```
Then walk runs, not paragraphs — formatting lives on the run:
```python
for r in re.findall(r'<w:r(?: [^>]*)?>(.*?)</w:r>', xml, re.S):
```

## Source identified and fact-checked — Cyber W02 Risk

**The booklet is a direct extraction of a real published textbook:**

> Sharp, R., "Risk", in *Introduction to Cybersecurity: A Multidisciplinary Challenge*, Undergraduate Topics in Computer Science, Springer, Cham, 2024, pp. 37–56. DOI 10.1007/978-3-031-41463-3_3

Robin Sharp — emeritus professor, Cybersecurity Section, **DTU Compute (Denmark)**. That explains the "liveware" term and the `K` (konsekvens) / `M` letters. **The stray `3` at the top of the DOCX was the chapter number, not a page number.**

**How to identify a source from a stripped booklet — the recipe that worked:**
1. Take the booklet's **opening sentence** and search it as an exact quoted phrase. It returned the Springer chapter as the only exact hit.
2. Treat **stray numbers** as chapter/section numbers, not page numbers.
3. Match the **figure numbering** ("Fig. 3.1", "Fig. 3.2/3.3") to the chapter's figure list.
4. Match the publisher's **chapter abstract** against the booklet's opening movements.
5. Confirm via the DOI on a second independent record (DTU Orbit, DBLP).
