### Reading a DOCX with no libraries — reusable recipe

There is **no `python-docx`** in either the managed venv or the system Python. Parse the zip directly:

```python
import zipfile, re, html
z = zipfile.ZipFile("file.docx")
xml = z.read("word/document.xml").decode("utf-8")
for p in re.split(r'</w:p>', xml):
    line = "".join(re.findall(r'<w:t[^>]*>(.*?)</w:t>', p, re.S))
    line = html.unescape(line).strip()
    if line: print(line)
```

**Check these three things before trusting the extraction** — all three bit me on this file:
1. `[n for n in z.namelist() if n.startswith("word/media")]` — **if empty, the document has no images at all**, even though the text says "Fig. 3.1", "Fig. ...". A text-only DOCX means every figure is a hole in the study material.
2. `"m:oMath" in xml` / `xml.count("<w:object")` — no OMML and no OLE means equations are **not real equation objects**; they are loose text runs.
3. `xml.count("<w:sym")` — Word encodes special glyphs (×, ÷, →) as `<w:sym>`. My `<w:t>`-only regex **silently drops them**. On this file the `×` and `/` operators were simply **gone**, leaving `S F K =` as separate paragraphs.

**Rule that follows from this:** when an operator is missing, do **not** guess it from the variable names. Reconstruct it only if the surrounding prose states the operation — here the booklet says "the result of the *multiplication*" and "the result of the *division*", which is a legitimate confirmation — and then still flag it `[VERIFY]` against the printed original.

## When the source is paywalled — verify the model on its own terms

Springer blocked the chapter PDF (bot challenge) and the book body is not publicly indexed. **Instead of stopping, I proved the equations mathematically.** That is a reusable move: a model can often be validated by its own behaviour without reading the source that printed it.

**The four tests that did the work — apply them to any formula you cannot look up:**
1. **Direction of effect** — differentiate. `∂R/∂M = −S/M² < 0` ⇒ residual risk falls as protection rises. Correct.
2. **Boundary conditions** — probe `M → ∞`, `M = 1`, `M = 0`, `0 < M < 1`. This is where it broke: `M = 0` divides by zero, and `0 < M < 1` yields residual risk *greater* than inherent risk. So the formula is well-formed **only on `M ≥ 1`**, which proves `M` is a **factor, not a count**.
3. **Dimensional check** — `[R] = [S]`, `[M]` dimensionless. Consistent.
4. **Equivalence proof** — substitute `M = 1/(1 − CE)` into `R = S/M` and it collapses to `S(1 − CE)`, the industry-standard form. So the division form is the mainstream model re-parameterised, not a rogue formula.

**And a logical contradiction test for reported content:** if a student reports two equations sharing a subject letter, check that every shared symbol keeps one meaning. Here `s` had to mean "frequency" in one and "risk" in the other — contradiction, so a mishearing, provable without the book. Also test the *claim*: a denominator of "number of threats" fails both direction (more threats → less risk) and the zero case (division by zero). **A defensive quantity belongs in the denominator; a threat quantity never does.**

**The two formulas, exam-safe:** `risk = frequency × consequences` (both must matter ⇒ multiply, never add); `residual risk = risk ÷ protection factor` (protection ≥ 1, never divides by zero).

## File 03 written — Prototyping and the Evolutionary Model

**Deliverable:** `Week_02_File_03_Prototyping_and_Evolutionary.md` — **471 lines / 49 KB, 36 verbatim quotations, 22 Arabic blocks, 61 page-anchor citations, 16-item retrieval set.** Smaller than File 02 (which covered four models) because this one covers two.

**The most valuable thing found, and it was not in the plan:** Sommerville supplies a **theoretical framework** that organises the whole series — **change avoidance versus change tolerance**.

- Change adds cost because completed work must be redone; this is **rework** (Sommerville p.61).
- **Change avoidance** = activities that *"anticipate possible changes before significant rework is required"* → **prototyping**.
- **Change tolerance** = a process designed so changes cost little, normally via **incremental development**, because the change lands in increments *"that have not yet been developed"*.
- Sommerville states the mapping himself: **prototyping supports avoidance; incremental delivery supports both.**

**That mapping is now the lens for Files 04–08** — every remaining model can be classified as one or the other, which gives the series a second organising axis alongside the File 02 "shortcoming → repair" table.

**Other new verbatim material:**
- **Brooks [1975]:** *"It is impossible to 'get it right' the first time… one must **plan to throw away the software** in order to develop a good software later."*
- The prototype as a ***"toy and crude implementation of a system"*** with deliberate shortcuts — Mall's own example is producing a result by **table look-up rather than performing the actual computation**.
- **"animated requirements specification"** (Mall p.93) — for GUI parts the approved working prototype makes the requirements-analysis phase redundant because the prototype *is* the specification.
- The two cases where prototyping wins: **the GUI part** (*"almost always developed using the prototyping model"*) and **unclear technical solutions** (the compiler example — a lack of familiarity with a required technology is a *"technical risk"*).
- **Sommerville's mechanism for why prototypes beat specifications:** *"A function described in a specification may seem useful and well defined. However, when that function is **combined with other functions**, users often find that their initial view was incorrect or incomplete."* The difficulty is in the **interaction**, not in the function.
- **The general problem with prototyping** and its three causes — an atypical tester, insufficient training time, and slow response teaching evaluators to avoid the slow features, so they use the final system differently.
- **Managerial pressure to deliver throwaway prototypes** when the final version is late.
- **The evolutionary model's distinguishing sentence:** incremental *"complete requirements are first developed and the SRS document prepared"*, whereas evolutionary **"the requirements, plan, estimates, and solution evolve over the iterations, rather than fully defined and frozen in a major up-front specification effort."* **The distinction is what gets frozen — not how many increments there are.**
- The nickname **"design a little, build a little, test a little, deploy a little"** — with **deployment inside the iteration**.
- **Sommerville p.60:** development and maintenance should be seen as a **continuum**, and software engineering as an *"evolutionary process"* — which is the theoretical justification for the evolutionary model.
- **Sommerville p.65:** the three system types where incremental delivery does not fit (very large, embedded, critical), and **prototyping as the resolution** — so the two models are complementary by system type, not competitors.

## File 04 written — Incremental Development

**Deliverable:** `Week_02_File_04_Incremental_Development.md` — **459 lines / 49 KB, 24 verbatim quotations, 19 Arabic blocks, 53 page-anchor citations, 16-item retrieval set.** Also **extended File 03 with a new §3.4** carrying Mall's prototyping strengths/weaknesses balance sheet (pp.94–95), which belongs to File 03's topic and is what closes it.

**Centre of gravity flipped.** Files 02 and 03 were Mall-primary. **This one is Sommerville-primary** — Mall's incremental section is only pp.95–97, while Sommerville supplies the definition, the three benefits, the two management problems, the large-system caveat, and the whole development-versus-delivery distinction. Recorded as a `[THIN]` note so a student does not assume Mall covers it.

**The key content:**
- **The definition:** *"developing an initial implementation, exposing this to user comment and evolving it through several versions"*; the activities are **interleaved rather than separate** (Sommerville p.49–50).
- **The naturalness argument:** incremental development *"reflects the way that we solve problems. We rarely work out a complete problem solution in advance but move toward a solution in a series of steps, backtracking when we realize that we have made a mistake."* This is an **argument about human cognition, not about technology**, and the later agile models rest on it.
- **Sommerville's three benefits:** reduced cost of change · easier customer feedback · more rapid delivery. The deepest is the second, because *"customers find it difficult to judge progress from software design documents"* — i.e. documents are not a working communication channel with the customer.
- **Mall's two advantages, which do not overlap Sommerville's at all:** **error reduction** (the core modules are used from the beginning, so they are tested thoroughly) and **incremental resource deployment** (the customer need not commit large resources at once). Flagged as a source-difference: if a question says "according to…", answer that source's set.
- **The core/non-core rule** (Mall p.96): core features are those that *"do not need to invoke any services from the other features"* — core means **independent**, and that is why it is built first.
- **Each increment is built with iterative waterfall** — so the incremental model **contains** another model. Models are not mutually exclusive.
- **The two management problems** (Sommerville p.51): **the process is not visible** (managers need deliverables to measure progress, and documenting every version is not cost-effective) and **system structure tends to degrade** unless money is spent on **refactoring**. Noted the productive tension: the waterfall **over-documents** (File 02 shortcoming 6) while incremental **under-documents** — neither solves the management-visibility problem.
- **The large-system caveat:** large systems need a **stable framework or architecture**, and *"this has to be planned in advance rather than developed incrementally."* Combined with Sommerville p.47 this yields a clean rule: **plan the architecture up front, develop the content incrementally.**
- **THE DISTINCTION THAT CARRIES MARKS — incremental *development* vs incremental *delivery*:** you can develop incrementally and *"expose it to customers for comment, without actually delivering it and deploying it."* Incremental **delivery** means the software *"is used in real, operational processes"*, and it is *"not always possible as experimenting with new software can disrupt normal business processes."*
- **The local-freezing rule** in incremental delivery: later increments can be re-analysed, but *"requirements changes for the current increment are not accepted."* This produced a three-step scale worth keeping: **waterfall freezes everything; incremental freezes the full requirements then the current increment; evolutionary freezes nothing.**
- **"No re-learning"** (p.64) — early increments serve as prototypes *"but unlike prototypes, these are part of the real system so there is no re-learning."* A delivered increment teaches the customer something that **stays**; a throwaway prototype teaches something that **disappears**.
- **The procurement conflict** (p.65) — the third problem with incremental delivery is **organisational, not technical**: *"the complete system specification is part of the system development contract"*, so incremental delivery *"requires a new form of contract, which large customers such as government agencies may find difficult to accommodate."*
- **The bureaucratic-mismatch sidebar** (p.51) — the primary cause of adoption difficulty is that *"large organizations have bureaucratic procedures that have evolved over time"*, some of them there for good reason (**Sarbanes-Oxley**), and *"changing these procedures may not be possible so process conflicts may be unavoidable."* This is the answer to "why doesn't every organisation use the better model?"

**Position in the series:** incremental is the **only model so far that scores on both change axes** — Sommerville states it supports **both change avoidance and change tolerance**. It repairs three waterfall shortcomings (long delivery, limited customer contact, no phase overlap) but leaves two (heavy documentation, no risk support), and it introduces a cost of its own: **it is slow**, because the customer waits for the last increment. **That slowness is the door into File 05 (RAD).**
