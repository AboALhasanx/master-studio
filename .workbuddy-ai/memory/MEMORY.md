## C. Authoring + RTL pitfalls (render-verified)
- YAML frontmatter with a REAL title (`title: ملزمة الويك N — <topic>` + `course:` + `subtitle:`); never the exporter default title.
- Content-type label per section; **EN lists SEPARATE from Arabic**; verbatim label INSIDE `>` block; "صفحة صفحة" = ① verbatim ② literal translation ③ my understanding.
- **RTL:** ordered lists scramble → `| # | … |` table; consecutive bold Q/A lines merge → `| السؤال | الجواب |` table or blank line; `inline code` with `_` or `/` reverses in Arabic → name the file in prose; trailing `(ص 103)` jumps to line start → drop it.
- **🚫 NO ASCII CODE in ملازم (STANDING, 2026-10-13, his explicit order, said twice).** Zero ` ``` ` fenced blocks in any study note. Replacement law (render-tested): calc/derivation → **plain paragraphs**, each line its own paragraph, blank line between (renders LTR fine under an Arabic label); step lists & folder trees → **two-column text tables**. Never a `#`/digit column when row content is Latin (bidi reverses the row) · never a blockquote `>` with consecutive lines (they merge) · never a markdown ordered list `1.` (number jumps to line end) · never a table cell starting with a digit (`200^1.12`→`1.12^200`). *Correction:* a Latin paragraph separated by blank lines does NOT flip (verified Ch04 p3).
- **⚠️ TABLE PARSING LAW** (caused 32 broken tables in Ch04 + more in Ch05). The exporter does NOT parse a markdown table if: (a) it is adjacent to the previous/next line without a blank line → collapses into scrambled bidi text; (b) the separator row's cell count ≠ the header's; (c) it is nested inside a list item (`- | # | ...` — never parsed). **Always: blank line before AND after · separator cells == header cells · never inside a list.** Detector: scan the PDF text layer for literal `|` — a parsed table never leaves pipes. Also watch unclosed backticks (odd count on a line) — they swallow the rest of the row.
