## 0. الملخّص التنفيذي

تيليكرام اليوم **موجود داخل الماستر ستوديو** كوحدة واحدة (`90_Shared_Toolbox/telegram/`) بمعمارية **صادرة فقط** (outbound-only، ADR D2): الوكيل يقود، البوابة تنفّذ، ولا شيء يقرأ الكروب.

الطلب الجديد يكسر D2 حرفياً — ولهذا نبني **طبقة تفاعلية مرسومة الحدود** بدل حلّها بحلقة استماع دائمة. الفكرة: **الردّ عند الطلب** — البوت لا يقرأ كل رسالة، بل يقرأ فقط ما يُستهدَف به (منشن أو أمر)، وبوابة موافقة صريحة لكل فعل إداري.

| الطبقة | حالياً | بعد هذا التغيير |
|:--|:--|:--|
| البوابة الصادرة | ✅ كاملة (G0–G4) | تبقى كما هي — لا تُلمس |
| الطبقة التفاعلية | ❌ غير موجودة | **جديدة**: `interactive.py` + بوابة موافقة |
| ذاكرة البوابة | ⚠️ موزّعة بلا حدود | **مجلد مرسوم**: `00_STUDIO_HUB/telegram/` |
| الوكيل يقرأ الكروب | ❌ لا | ✅ **بس عند الطلب**، وبقائمة سماح |

## 1. المشكلة: الحدود الحالية غير مرسومة

البوابة اليوم تكتب في **ثلاث ذاكرات متداخلة بلا حدود معلنة**:

| الذاكرة | المسار | من يكتب؟ | الحدود |
|:--|:--|:--|:--|
| حالة تشغيل حيّة | `telegram/registry.json` + `gateway.db` | البوابة | gitignored (D10) — واضحة |
| ذاكرة المشروع المشتركة | `00_STUDIO_HUB/MEMORY.md` + `ACTIVE_STATE.md` | **البوابة والوكيل معاً** | ❌ **غير مرسومة** |
| ذاكرة الوكيل | `.workbuddy-ai/memory/` | الوكيل فقط | غير معلنة |

**الخلل الحقيقي:** لا يوجد "مالك" واضح لذاكرة البوابة. تيليكرام يكتب في ذاكرة الماستر ستوديو كما يشاء، ويقرأ منها كما يشاء — بلا عقد.

## 2. القرار D14 — ذاكرة البوابة (`00_STUDIO_HUB/telegram/`)

### المبدأ: **طبقة مستقلة، بواجهة ضيّقة — مو انعزال**

مجلد بذاكرة **خاصة بالبوابة**، لكن مربوط بالذاكرة الأم عبر عقد قراءة/كتابة صريح:

```
00_STUDIO_HUB/
├── MEMORY.md                 ← ذاكرة الماستر ستوديو الأم (تبقى للمشروع)
├── ACTIVE_STATE.md           ← حالة المشروع
└── telegram/                 ← ★ ذاكرة البوابة (جديدة)
    ├── README.md             ← العقد: شو من حق البوابة تكتب وين
    ├── TELEGRAM_MEMORY.md    ← ذاكرة البوابة: سجل النشر، تفضيلات، قراراتها
    ├── STATE.md              ← الحالة: آخر نشر، آخر منشن، صحة القناة
    └── log/
        └── YYYY-MM-DD.md     ← سجل يومي ملحق-فقط (append-only)
```

### العقد (interface) — من حقّ من، شو:

| الاتجاه | القاعدة |
|:--|:--|
| **البوابة → ذاكرتها** | ✅ حرّة تماماً (سجل النشر، الحالة، التفضيلات، الأخطاء) |
| **البوابة → ذاكرة الأم (`MEMORY.md`)** | ⚠️ **بإذن الوكيل فقط** — البوابة لا تكتب مباشرة في ذاكرة الماستر ستوديو |
| **البوابة ← ذاكرتها** | ✅ تقرأ حرة |
| **البوابة ← ذاكرة الأم** | ✅ قراءة حرة (تحتاج السياق: أي مواد، أي توبيك) |
| **الوكيل → ذاكرة البوابة** | ✅ يقرأها ويحدّث الحالة عبر واجهة معلنة |

**لماذا هذا مهم:** البوابة تصير **طبقة**، مو **رَقَم في ذاكرة الأم**. لو حبيت لاحقاً تنقل البوابة لمشروع ثاني، ذاكرتها تنتقل معها.

### التنفيذ
- دالة صغيرة `telegram_memory.py` (وحدة جديدة) توفّر: `record_post()`, `last_state()`, `append_log()`, `read_prefs()`.
- لا SQLite — ملفات Markdown/JSON بسيطة (البوابة أصلاً تستعمل `registry.json`).
- سكربت `TG_MEMORY.md` يوثّق العقد.

## 3. القرار D15 — الردّ عند الطلب (بدل حلقة دائمة)

### لماذا مو `getUpdates` دائم؟

`getUpdates` الدائم يعني: خدمة تشتغل 24/7 + سطح هجوم + تكلفة استضافة + البوت يقرأ **كل** رسالة في الكروب. كل هذا يكسر D2 ويرفع الخطر بلا داعي.

### البديل: **جلسة استماع واحدة** (One-shot listener)

```
                 نمط D15 — الردّ عند الطلب
  ┌──────────┐   ①  يكتب منشن/أمر    ┌─────────────┐
  │  طالب    │ ────────────────────▶ │   الكروب    │
  └──────────┘                       └──────┬──────┘
                                            │
                       ② الوكيل يبدأ جلسة استماع قصيرة (بدل دائمة)
                                            │
                     ┌──────────────────────▼──────────────────────┐
                     │  interactive.py listen --once               │
                     │  • getUpdates (offset محفوظ، offset_confirmed)│
                     │  • يفلتر: منشن للبوت؟ أمر؟ من قائمة السماح؟ │
                     │  • يستخرج: actor, chat, text, message_id     │
                     └──────────────────────┬──────────────────────┘
                                            │
                          ③ يبني الردّ حسب المحتوى
                                            │
                     ┌──────────────────────▼──────────────────────┐
                     │  reply بناءً على: النص + السياق + القدرة     │
                     │  • سؤال عن مادة؟ → يجاوب/يجيب رابط          │
                     │  • أمر إداري؟ → ★ بوابة الموافقة (D16)      │
                     │  • غيره؟ → يردّ بحدود القدرة                │
                     └──────────────────────┬──────────────────────┘
                                            │
                          ④ sendMessage (reply_to_message_id) — مسار صادر موجود
```

### الفرق الجوهري عن الحلقة الدائمة

| | حلقة دائمة (D2 الأصلي) | جلسة واحدة (D15) |
|:--|:--|:--|
| مدة التشغيل | 24/7 | دقائق عند الطلب |
| يقرأ | كل رسالة | فقط ما بين offset ووقت الإغلاق |
| استضافة | لازم | ❌ لا — يعمل على حاسبتك عند الطلب |
| يكسر D2 | ✅ نعم | ❌ **لا** — يضيف **D15** كتوسعة مرسومة |
| البوت يردّ فوراً | ✅ | ⚠️ عند تشغيل الجلسة |

**التنازل الوحيد:** الردّ مو فوري 24/7 — يحتاج جلسة مفتوحة. لكن لو احتجت 24/7 لاحقاً، نفس الوحدة تدعم `--daemon` (توسعة، مو إعادة كتابة).

### القيود الحاسمة
- **قائمة سماح صارمة (fail-closed):** `getUpdates` لا يُشغَّل أصلاً إلا لو `TELEGRAM_CHAT_ALLOWLIST` محدّدة.
- **بصمة offset:** نحفظ `update_id` الأخير معالج في ذاكرة البوابة — لا نقرأ رسالة مرتين، ولا نضيّع رسالة.
- **حدّ زمني:** كل جلسة لها `--for <seconds>` (افتراضي 60) و`--max <n>` رسالة — لا جلسة مفتوحة بلا نهاية.
- **وضع الخصوصية:** لو البوت مو قادر يقرأ رسائل الكروب (privacy mode)، الجلسة تفشل بوضوح وتطلب ترقية البوت لأدمن/إعادة تعيين الخصوصية.

## 4. القرار D16 — بوابة الموافقة الإدارية (أنت الأدمن)

طلبك: *"الأوامر الإدارية للكروب تطلب موافقتي أنا الأدمن"*.

### المبدأ: **الافتراضي = لا شيء إداري**

كل فعل إداري (`delete`, `pin`, `unpin-all`, `topic close/delete`, `ban` مستقبلاً) يمرّ ببوابة صريحة:

```
   أمر إداري وصل من الكروب
            │
            ▼
   ┌────────────────────────┐
   │ هل actor ∈ TELEGRAM_OWNER_IDS؟ │
   └───────┬────────────┬───┘
           │ نعم        │ لا
           ▼            ▼
   ┌──────────────┐  ┌──────────────────────┐
   │ يطلب موافقة   │  │ ★ إرفاق مرفوض + تدقيق │
   │ عبر الوكيل    │  │ "هذا الفعل يحتاج     │
   │ (D16 gate)   │  │  موافقة الأدمن"       │
   └──────┬───────┘  └──────────────────────┘
          │
          ▼
   الوكيل يسأل أبو الحسن: "طالب فلان يريد يحذف رسالة X — توافق؟"
          │
     ┌────┴────┐
     │ نعم     │ لا
     ▼         ▼
   ينفّذ    يردّ "مرفوض"
   + تدقيق
```

### الطبقات الثلاث
1. **قائمة المالك في الكود** (`acl.py`) — موجودة أصلاً. لو الفاعل مو مالك → رفض فوري.
2. **`--confirm`** — موجود أصلاً للأفعال المدمّرة (D7).
3. **جديد — `approval.py`**: يربط الفعل الإداري بطلب موافقة **يتجاوز CLI** (يرسل للأدمن في الخاص أو يظهر للوكيل ليتأكد منك).

### الشكل العملي
- الفعل الإداري يوصف في **طلب معلّق** (`pending_approval.json`).
- الوكيل يعرضه عليك: *"فلان يريد: حذف رسالة #123 — توافق؟"*
- توافق → يُنفَّذ ويُسجَّل. ترفض → يُسجَّل مرفوض.
- **لا فعل إداري يُنفَّذ بلا موافقتك، أبداً.**

## 5. حدود الأمان (الطبقة الجديدة)

| الخطر | الحماية |
|:--|:--|
| البوت يقرأ كلام خاص بدون حق | `getUpdates` ممنوع إلا على `TELEGRAM_CHAT_ALLOWLIST` (فشل مغلق) |
| رسالة تُقرأ مرتين / تضيع | `update_id` offset محفوظ في ذاكرة البوابة |
| جلسة استماع بلا نهاية | `--for <seconds>` + `--max <n>` (حدّان، افتراضيان) |
| فعل إداري بدون إذن | بوابة D16: افتراضي = رفض، موافقة الأدمن إجبارية |
| منشن من غريب | رفض + تدقيق — قائمة المالك هي الفيصل |
| انفجار تكلفة | الجلسة عند الطلب، مو دائمة |

## 6. ما **لا** نغيّره

- ❌ **البوابة الصادرة (G0–G4)** تبقى كما هي — لا لمس.
- ❌ **`registry.json` / `gateway.db`** يبقون حالة تشغيل (D10 كما هو).
- ❌ **البوت الرسمي فقط** (D1) — لا MTProto / حساب مستخدم (يبقى #22).
- ❌ **`--confirm` للأفعال المدمّرة** (D7) — يبقى، وD16 يضيف فوقه.
- ✅ **`MEMORY.md` الأم** تبقى لمشروع الماستر ستوديو — البوابة صارت لها ذاكرة خاصة.

## 8. الأسئلة المفتوحة (تحتاج قرار أبو الحسن)

1. **جلسة الاستماع:** تريدها **يدوية** (تقول "يا كوكو، افتح جلسة" وتشتغل X دقيقة) أم **مجدولة** (تشتغل تلقائياً كل فترة)؟

4. **النطاق الأول:** نبدأ بالكوز والمواد (آمن) أم نجرّب منشن عام أول؟
