## Codex — ASE Chapter 7 reliability omissions: source-backed web review (2026-10-23)

Scope: research-only follow-up to the four instructor-requested points. No Chapter 7 deliverable was edited.

- **Goel–Okumoto source-boundary correction:** The official Ch07 book OCR and instructor slide extraction found in the Reliability_Seminar source set do not name Goel–Okumoto in the teaching text (the surname Okumoto appears in bibliographies). However, the separately stored `sources/UoM_Reliability_Lecture.txt` (Dr. Najla Al-Saati, not the course instructor's companion deck) explicitly names “Goel-Okumoto Model (GOM)” and gives its finite exponential mean-value form. Therefore “absent from all sources” is too broad unless this supplementary lecture is explicitly excluded; it remains absent from the identified course-primary prose/deck. The 1979 original is Goel & Okumoto, “Time-Dependent Error-Detection Rate Model for Software Reliability and Other Performance Measures,” DOI 10.1109/TR.1979.5220566. Derivative: `m(t)=a(1−e^(−bt))`; `λ(t)=ab e^(−bt)`. Do not conflate this finite NHPP with Musa–Okumoto's logarithmic Poisson execution-time model.
- **Curve pairing:** Supported as a page-layout improvement, not a missing concept. Keep hardware bathtub and software reliability curves as two panels with their own captions/axes. Hardware bathtub describes early-life/useful-life/wear-out behavior; software does not physically wear out, and its reliability-growth curve reflects failure detection/correction under stated testing/use conditions. Avoid implying identical mechanisms or an undifferentiated shared scale.
- **Basic vs logarithmic table:** Existing T3 Comparison 7.5 already contains the comparison content in prose, so the deficiency is presentation/scanability rather than absent information. The four-column table is justified as a study aid. Label the asymptote column precisely: Basic has finite cumulative failures `μ(τ)→v0`; Musa–Okumoto has no finite cumulative-failure limit (`μ(τ)→∞`). In both, failure intensity tends to zero; Basic reaches zero at `μ=v0`, while log-Poisson approaches zero asymptotically. Selection should follow the finite/infinite-failure assumption and empirical fit, not a universal “better model” claim.
- **Operational profile:** The textbook passage and the primary OP literature support the main point: software reliability is conditional on specified usage/operational profile; varying operation weights can yield different measured reliability for an unchanged software version when operations have different failure probabilities. Phrase it conditionally (“can differ”) and specify same build/environment/mission measure. Simple per-demand model: `R(OP)=Σ_i p_i R_i`; profile weights matter when per-operation reliabilities differ. The causal intuition “defects on common paths matter more” is reasonable; avoid implying every operational-profile change necessarily changes reliability.

Web evidence reviewed: National Academies, *Reliability Growth: Enhancing Defense System Reliability*, DOI 10.17226/18987, https://doi.org/10.17226/18987; Springer, Musa & Okumoto, *Application of Basic and Logarithmic Poisson Execution Time Models in Software Reliability Measurement*, DOI 10.1007/BFb0034284, https://doi.org/10.1007/BFb0034284; Musa, “Operational Profiles in Software-Reliability Engineering,” DOI 10.1109/52.199724, https://doi.org/10.1109/52.199724; “Reliability of Software with an Operational Profile,” https://doi.org/10.1016/S0377-2217(02)00461-7; NIST bathtub curve handbook, https://www.itl.nist.gov/div898/handbook/apr/section1/apr124.htm; NASA software reliability guidance, https://swehb.nasa.gov/pages/viewpage.action?pageId=72024565.

## OpenCode — delete-account + PIN audit on the tablet (2026-10-23)

Tested both flows on the device (`AJ5EJK5913W00158`) with a throwaway account (`qa420422`, then deleted).

**Delete my account — works, one leak.** confirm → prompt → wrong PIN gives «الرمز غير صحيح» and keeps the
account; the right PIN deletes the server rows (`portal_users`, `league_xp`, `portal_data`, `login_links`,
`login_attempts` — verified: the handle is gone from the REST API), clears history/saved/best locally and
shows «تم حذف الحساب — نراك». **But `portal_pin_v1` survives the deletion** (and an explicit sign-out):
`signOut()` only removes the account + sync keys. That is the bug to fix — the PIN is the only credential,
and the profile field shows it in clear text.

**Change the 4-digit PIN — does not exist.** `portal_profile` verifies the PIN and never writes it; there is
no `portal_change_pin` RPC and no new-PIN field. Typing a different PIN into «رمزك (4 أرقام) لتأكيد التعديل»
and saving returns «أعد تسجيل الدخول لتعديل الملف» (misleading — the PIN was wrong) and burns one of the five
attempts (then a 5-minute lock). Proved against the API: old PIN `ok`, attempted new PIN `bad_pin`.

**Visual note:** the account page opens at scrollY 0 with the name/PIN in view; the earlier "button covered
by avatars" was the Android soft keyboard opening/closing during a scripted `fill`, not a layout defect.

**Portal hygiene:** the CI security spec leaves `sectest*` accounts behind — 25 of them had accumulated, plus
their league/data/link rows. Removed; the portal now holds only the student's real row
(`u:e36bc830…`, ابو الحسن) and one junk `u:None` fixture (also removed). Worth making the spec clean up after
itself.

**Fix shipped for the delete-account leak (1.4.5).** `signOut()` and `deleteAccount()` now remove
`portal_pin_v1`; `saveProfile` distinguishes `bad_pin` («الرمز غير صحيح») from a sync/session problem.
Verified on the tablet at 1.4.5: wrong PIN keeps the account and says the PIN is wrong, right PIN deletes it
and leaves `portal_pin_v1 = null`. Two notes learned the hard way: (a) a page opened before the deploy keeps
the *old* JS until it reloads — the first tablet run still leaked the PIN for that reason, so a shell update

`sectest*` accounts behind when its `finally` cleanup is throttled — 25 had accumulated, removed again.
